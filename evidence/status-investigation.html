## 1. Waitlisted on the already-open event card

**Verified backend behavior:** the original exact-entry API assertion recorded `waitlisted` before manager confirmation: 19:07:11 UTC for Single Event and 19:10:55 UTC for Regional. Both checks passed. These are historical states; the now-confirmed entries were not changed back to recreate a waitlist.

**Observed UI:** the already-mounted card remained Ready for entries/Register during the original 20-second check. Later retained-tab recordings showed Waitlisted. The original failed checks and both recording stages remain available.

**Classification:** an application cache/update gap across separately mounted pages, not evidence that entry creation failed. The test used the correct record. Each browser page has its own query client; invalidating the registration page's event query does not invalidate another open page's cache. The inspected `useAthleteEvents` has no polling, and the query-client defaults disable window-focus refetch. No automatic event/roster request was observed in the regional diagnostic's bounded 10-second window. One late request occurred in the adult observation, so the report does not claim every window had zero requests.

**Suggested fix:** propagate entry updates to mounted Event Lists (for example, a status notification/subscription or bounded polling while entries are pending). Invalidate the affected athlete/event query after entry mutations and arrange cross-tab updates if other open tabs must update. Do not insert refresh into the no-refresh assertion; refresh is a separate diagnostic.

## 2. Collected on Tour Manager roster

**Verified backend behavior:** GET /tour-manager/events/{eventId}/entries returned HTTP 200, with the exact entries `entry.code=confirmed` and `payment.code=collected`, for both scenarios. The original manager confirmation and backend collection checks also passed.

**Before/after refresh:** the retained Regional roster still displayed Pending while its live API already returned Collected. Explicitly refreshing that same event and reopening its Athletes tab displayed Collected/Confirmed. The original Single Event manager window had been closed, so that comparison uses its original Pending recording against a fresh exact-event load and refresh; it is not described as a refresh of that original window.

**Classification:** application refresh gap after asynchronous collection. `useConfirmField` invalidates the roster once when the command succeeds. Collection finishes later; `useSeedList` has no follow-up polling/subscription. The roster can therefore retain the initial Pending response even though the payment service has completed collection. The fresh page correctly renders Collected, ruling out the original payment-failed interpretation and a simple Pending/Collected selector error.

**Suggested fix:** refetch or subscribe to roster/payment updates until all affected charges reach a terminal state. Keep retries bounded, stop polling on terminal outcomes, and surface genuine provider failures independently.

## 3. Confirmed on athlete event card

**Verified backend behavior:** both exact manager entries are confirmed; both athlete confirmation-reference endpoints answer Confirmed insured. The event list's current response contains `selected: Selected` and `ready_to_compete: Ready to Compete`, with no Register action.

**Before/after refresh:** the retained Regional card still showed Waitlisted/Coverage Confirmed before refresh. Refresh changed it to Selected/Ready to Compete, matching the live event-list response, and removed Register. The earlier original recording showed the still older Ready for entries/Register state.

**Classification:** two distinct findings. The stale Register/Waitlisted card is an application update/cache issue. Requiring the exact visible text Confirmed is also an automation/contract wording mismatch against the current response: this API presents a confirmed entry as Selected/Ready to Compete. The test should validate the agreed status code/mapping rather than assuming the manager and athlete screens use identical wording. If the product requires the literal label Confirmed, that is a separate copy/contract change. The original failure is preserved and has not been relabelled passed simply because refresh fixes it.

**Suggested fix:** deliver live event-list updates as above, and align the assertion with the documented athlete-card status mapping. A refresh-only diagnostic passed for both records; the original no-refresh checks remain failed.
