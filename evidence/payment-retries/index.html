Detailed interpretation of the result counts

The 12 live results are assertions within several related scenarios, not 12 independent end-to-end payment journeys. They cover configuration reads, fixture state, two sequential retries, same-key replay, parallel distinct-key requests, two withdrawn states, and absence of collection. The 12 clock checks are source-function assertions against an advanced test clock, not 12 dev CronJob runs.

A passing “no success” assertion is a negative observation in the retained history. It does not establish that Stripe tried the card and declined it again. In this run, the card had already become inactive and payment recorded that it was not attempted.

Live scenario 1 — sequential manual retries

  1. Read the event roster and confirm the retained QA entry is Declined.
  2. Read its history as the baseline.
  3. POST {"code":"retry"} using a new idempotency key.
  4. Poll the history for a new outcome.
  5. Repeat with a second fresh key and inspect the final history.

Observed: both requests returned HTTP 200. Neither produced a success; the subsequent history states that the pinned saved payment method is no longer active.

Conclusion: the active declined entry can submit sequential retry requests. Recovery using a newly valid card was not repeated here; see the linked earlier valid-card report.

Live scenario 2 — duplicate requests with the same key

Two concurrent POST requests used the same entry, same retry body and the same Idempotency-Key. Their start times were one millisecond apart. Both returned HTTP 200.

The recorded history gained one outcome. That is consistent with idempotent replay: a successful replay response does not imply a second attempt. The automated assertion permits at most one outcome; the actual observed count was exactly one.

Limit: this is application-history evidence. Provider-side request and PaymentIntent counts were not queried, and this inactive-card fixture did not reach a new card charge.

Live scenario 3 — competing requests with different keys

Two concurrent retry requests targeted the same active declined entry with different idempotency keys. One returned HTTP 200; the other returned HTTP 409 with competition.entry_not_retryable. History gained one new outcome.

Conclusion: only one request won the retry claim in this observed race. This does not establish behavior under every ordering, a process crash, delayed payment events or withdrawal running concurrently.

Live scenarios 4 and 5 — retries on settled withdrawn entries

Withdrawn after decline: a fresh retry request returned HTTP 409. The captured history before and after that request contains the same items, so no new outcome was observed during the polling window.

Withdrawn after valid-card payment: a retry request returned HTTP 409 with competition.entry_not_retryable. This verifies the response for that later settled state; no new payment outcome was separately polled for this second fixture.

Why this matters: these tests ran later than the earlier immediate-withdrawal scenario. They verify the current settled states only. They cannot invalidate the earlier HTTP 200 or establish that the immediate removal window is safe.

How the 24-hour and 72-hour waits were bypassed

  1. Read the current dev schedule, rather than changing it: retries at 24 and 72 hours, grace at 168 hours.
  2. Load the local domain scheduling functions and extract the actual scheduler _work function without modifying its body.
  3. Provide an isolated charge, in-memory stores, captured command/notification sinks and a test clock anchored at 20 October 2026, 12:00 UTC.
  4. Invoke the scheduler at hour 23, hour 24 and immediately after hour 24. Verify no early dispatch, one due dispatch and no duplicate while waiting for an answer.
  5. Use the real domain function to calculate the next due time after a simulated retryable failure, then set the in-memory charge to that scheduled state.
  6. Invoke at hour 71 and hour 72. Verify only the due invocation dispatches the next attempt.
  7. Put the in-memory entry into Withdrawn before another due check, and verify stopping with no additional command.
  8. Check that a non-retryable decline has no due retry and that hour 200 does not dispatch an excessively late retry.

No actual days passed and no clock on dev was changed. The command sink captured objects in memory; it did not publish to NATS or contact Stripe.

Clock-test boundaries and what they do not prove

The isolated probe uses injected stores and command sinks. It exercises the scheduler branch decisions, attempt-key construction and domain due-time calculation. It does not run the real SQL repository, row-level security, FOR UPDATE SKIP LOCKED, outbox relay, consumer idempotency, notification delivery or provider webhooks.

The hour-73 withdrawn case is a deliberately prepared due row used to exercise the stop guard. It is not an additional configured third retry. The hour-200 case checks no retry dispatch after the deadline tolerance; it does not assert every grace-expiry notification or flagging side effect.

Backend path and findings to carry forward

  • Manual retry: BFF action handler → competition retry_payment_prepare → atomic charge claim → execute command → payment eligibility check → payment result/history.
  • Scheduled retry: one-pass competition.payment_retry job → tracked charges → entry-place check → due-time check → execute staged on the outbox.
  • Card replacement: an explicit update for a failed charge can trigger an immediate retry independently of the next automatic due time.
  • Withdrawal: local cancellation and an asynchronous payment release can overlap an already-sent or running attempt. The earlier report remains the evidence for that concern.

Current dev settled-state responses do not show whether terminal-entry validation was added, the scheduler cancelled the charge later, or another state transition removed eligibility. Database and message traces are needed to attribute the change in behavior.

Remaining verification plan

  1. Create an isolated entry with a provider failure classified as retryable, not an inactive card.
  2. With dev database/job access, identify the exact organisation, entry, charge and deferred-charge records. Preserve their UUIDs and request identities.
  3. Control only that fixture’s due time or run a scoped test clock; do not shorten global rules for other athletes.
  4. Prove worker invocation, outbox dispatch, provider request and webhook reconciliation for each retry.
  5. Repeat withdrawal before dispatch, after dispatch, during provider processing and after success. Include an alternate taking the vacant seat.
  6. Correlate execute and release IDs with PaymentIntent timestamps; confirm the original athlete is never silently re-added and any successful payment is visible for Finance resolution.
  7. Verify duplicate deliveries, crash recovery and refund idempotency where a refund is required by policy.
