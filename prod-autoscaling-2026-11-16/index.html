Production autoscaling and load test

Read-only check of how the WSL Pro production cluster (Python platform, EKS, us-west-2) is set up to scale, followed by a k6 load test against public pages. The configuration is healthy. The load test was stopped by the AWS WAF rate limit before the cluster needed to scale, so scale-out under load is still untested.

Summary
  • Configuration: healthy. A 3-node base group plus Karpenter (4 extra nodes now, limit 400 CPU). Six services autoscale (HPA). Nothing is pending.
  • Performance: fast. Up to 50 requests/s, the median response was 0.24 s and p95 was 0.66 s. Server CPU barely moved (frontend 7%, BFF 2%).
  • Blocked: the AWS WAF rate limit blocked the single test machine (HTTP 403) after about 3 minutes, so no HPA or Karpenter scale-out was triggered. The spike and endurance tests were not run.
  • Risk: payment, notification, support and sync run a single copy with no autoscaling.

5. Risks found

  1. No autoscaling, single copy: payment-api, notification-api, support-api, sync-api. A restart or node consolidation briefly takes them down, and they can't grow under load. payment-api matters most (charges and refunds).
  2. No autoscaling: trust-api is fixed at 2 copies. Queue workers (athlete-consumer, bff-consumer, bff-relay, iam-consumers, iam-relay) and competition-scheduler run 1 copy each. That may be by design, but it needs confirming.
  3. ai-api already runs at 47% CPU against a 50% target, with a max of 6 copies.

6. To finish the load, spike and endurance tests

  1. A temporary WAF allow rule for the test source (its IP, or a secret test header), placed ahead of the rate-based rule, for an agreed window only, and removed afterwards. Alternatives: distributed load (for example k6 Cloud) agreed with the platform team, or tests from inside the VPC.
  2. An agreed time window and stop limits. Proposed: load 20 → 300 req/s in steps; spike 10 → 400 req/s for 2 min; endurance 50 req/s for 30 min. Abort above 2% errors or p95 above 3 s.
  3. During the test, record HPA replicas, Pending pods and new nodes every 15 s, plus time to scale out and back in.

Method: Kubernetes API GET requests only (nodes, pods, HPAs, deployments, events, Karpenter NodePools and NodeClaims), EKS and Auto Scaling describe calls, and k6 v1 against public URLs. Nothing in the cluster was created, changed or deleted. Account identifiers, user names, keys and IP addresses are left out of this public page.
